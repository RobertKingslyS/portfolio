Migration · Kubernetes · CI/CD

A legacy service moved to Kubernetes, without a big-bang cutover

ProblemA customer-facing SSO-configuration service still ran on two virtual machines behind a classic load balancer, built by a legacy CI tool and deployed by hand.
What I didContainerised it (multi-stage image, one image for web and worker), gated publishing on its test suite, automated semantic releases with image promotion across registries, wrote the Kubernetes manifests (probes, disruption budgets, external secrets) and launched it dark on both production colours.
OutcomeReleases flow from merge to production automatically, and the new stack runs dark in production with no customer impact. Two compatibility risks were caught before cutover: API path versioning, and a job queue shared by the old and new workers.
Request flow · before
Admin action→App backend→DNS→Classic load balancer (TLS)→2 VMs · web + worker→Redis job queue→SaaS provider API
Request flow · after
Admin action→App backend→DNS→Global edge accelerator→Gateway API ingress→Kubernetes Service→Web & worker pods→Redis job queue→SaaS provider API
Release pipeline
Merge→Scan→Test→Semantic version→Registry replication→Dev→Staging E2E gate→Production (dark)→Cutover (planned) · instant DNS rollback
Security · Change management

Global TLS certificate renewal with zero downtime

ProblemOneLogin's annual renewal of external and internal-domain certificates spans four AWS regions and many load balancers.
What I didLed 62 CAB-approved change steps: CSR and key generation with hash checks, Terraform and ACM rollout, ARN updates in Terraform Enterprise, and validation with OpenSSL and cURL across NLBs, ALBs, mobile and CDN endpoints, with rollback-ready backups.
OutcomeZero downtime, tighter audit compliance and a reusable runbook for future renewals.
Security · Edge

Firewall hygiene backed by traffic data

ProblemAllowlist entries let traffic skip the edge rate limit, and many of them had gone stale.
What I didRan a 30-day traffic analysis, then removed entries in staged batches, each with a rollback artifact and post-change checks.
Outcome370+ unused entries retired, leaving a smaller and easier-to-audit allowlist. During security escalations, targeted IP and geo rules shipped through the same process.
Data · Automation

Self-healing routing after database failover

ProblemAfter a managed-database failover, the network load balancer kept pointing at the old database address until someone fixed it by hand.
What I didBuilt event-driven automation (database events → SNS → Lambda) that registers the new address with the load balancer, rolled out region by region with Terraform.
OutcomeOne manual, high-pressure step removed from every database failover.
Reliability · Capacity

Capacity and memory fixes under incident pressure

ProblemQueue backlogs, out-of-memory restarts and database write throttling during peak load.
What I didTuned event-driven autoscaling limits, aligned memory limits across regions, raised database autoscaling floors and codified them in Terraform, and added a fail-fast timeout for a slow upstream dependency.
OutcomeBacklogs drained, restarts stopped, and throttle alerts now recover on their own.
Observability

Alerts people trust

ProblemSome monitors were noisy or permanently red, and some services had no per-region view.
What I didBuilt per-service, per-region dashboards aligned to the public status page, added deploy markers for deploy-aware alerting, retired duplicate monitors and fixed false pages after an agent migration.
OutcomeFewer false pages and faster triage for the on-call engineer.
